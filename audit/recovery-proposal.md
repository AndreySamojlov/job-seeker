# Предложение восстановления Job Machine

Статус: историческое предложение; 15 октября 2026 пользователь выбрал сохранение обоих путей заполнения. Актуальный замысел — [Product Intent](../docs/product-intent.md), техническое предложение — [спецификация восстановления](../docs/superpowers/specs/2026-10-15-job-machine-recovery-design.md). Продукт ещё не перенесён. Основание: [аудит](recovery-audit.md).

## Цель из поручения

Выделить полезные проверяемые компоненты существующего Job Machine в один сопровождаемый проект по модели артефактов Codex. Сохранить вакансии, оценки, материалы, историю отправок и доказательства. Отделить фактическое поведение от пожеланий и исторических планов. Исходные проекты не уничтожать.

## Предлагаемый продукт

Сохранить существующую предметную область: несколько кандидатов, discovery → verification → оценка по подтверждённым фактам → резюме и пакет → заполнение → управляемая отправка → подтверждение и исход работодателя. Не добавлять в рамках восстановления новые продуктовые функции. Повторно использовать небольшой dashboard и MCP; расширение UI проводить отдельным определённым срезом, если потребуется.

Решение принято: сохраняются оба пути заполнения. Ниже сохранены рассмотренные варианты для истории; выбор больше не открыт.

- **Рекомендуется:** сохранить оба пути. Детерминированный worker обрабатывает поддержанные формы; агент помогает на нестандартных формах. Оба используют общий контракт фактов, согласий, одобрения и доказательств. Возможность сохраняется в новом проекте, её выпуск требует отдельной проверки.
- **Альтернатива:** оставить только детерминированный путь. Меньше компонентов, но это сознательное сокращение существующего поведения; неподдержанные формы останавливаются для участия человека.

Ни один вариант не означает разрешения отправлять заявки в ходе аудита или автоматически активировать новую сборку. Исторические утверждения об авторизации не заменяют определение действующей политики для нового продукта.

## Подход к переносу

1. Целевой каталог — текущий `C:\Users\samoj\Documents\ChatGPT\Job Seeker`, продукт называется Job Machine. Одна новая рабочая база с provenance исходных коммитов; старые Git-репозитории остаются доступными.
2. `master=842e46a` — база сравнения с прошедшими локальными тестами. Состав работающего production описывается отдельным manifest. Код из production-веток и Codex переносится выборочно после сравнения и проверки; прямое копирование всего checkout исключено.
3. Секреты, браузерные профили, резюме и runtime-том не входят в versioned source. Операционная БД и файлы сохраняют единого владельца. До любых миграций/переключения — backup и проверка восстановления в изолированном контуре.
4. Первая новая сборка изолирована от рабочей очереди; отправка выключена. Приёмка через локальные формы и тестовую БД. Production продолжает работать на текущих образах до отдельно подготовленного переключения.
5. Перенос завершается не копированием, а воспроизводимым запуском, проверками контрактов, связности данных/артефактов и журналом исключённых либо отложенных компонентов.

## Артефактная модель

| Артефакт | Авторитетное содержание |
|---|---|
| Product Intent | Согласованная цель, сценарии, ограничения и модель автономности; открытые решения явно обозначены |
| Functional Specification | Только поведение перенесённой и проверенной версии, статусы и исключения |
| Architecture | Границы компонентов, runtime, отказоустойчивость, configuration и launch |
| Component Map | Ответственность и контракты модулей; ссылки на код |
| Data Architecture | PostgreSQL, артефакты, пути/хеши, владение, история и восстановление |
| User Journeys | Реализованные пути оператора через MCP/dashboard, блокировки и продолжение |
| Design System | Существующие UI-правила панели; отсутствие полноценной системы компонентов отмечается явно |
| Test Strategy | Изолированные тестовые среды, критичные инварианты, integration/browser/E2E и release gates |
| Project Knowledge | Decisions, Observations, Lessons, Trust; текущий аудит становится основанием, а не заменой всех регистров |
| Decomposition Map | Один канонический backlog Project → Epic → Story → Task, углубляемый по выбранному срезу |

## Предлагаемые срезы после согласования замысла

Сначала восстановить воспроизводимую базу и наблюдаемость; затем свести необходимые runtime-различия; затем провести проверку данных и приёмку; после этого подготовить доставку. Полный продуктовый Intent сохраняется во всех срезах. Это последовательность результатов, не готовая декомпозиция или утверждённый implementation plan.

## Критерии результата

- Ясно, какой commit и какой образ реализует каждую возможность.
- Из чистого окружения воспроизводимо запускаются нужные компоненты.
- Сохранены данные и все необходимые связи с файлами; неизвестные исходы не превращены в повторные отправки.
- Unit, DB, browser и выбранные synthetic E2E подтверждают перенесённое поведение.
- Документация соответствует этой проверенной версии, содержит ограничения и не объявляет исторические намерения фактами.
- Старые копии остаются архивными источниками, новый проект имеет один набор действующих инструкций.

## Следующее решение

Выбор обоих путей зафиксирован в Product Intent. Следующий шаг — рассмотрение подготовленной спецификации восстановления, затем Staging, Decomposition Map и план исполнения. Новый продукт пока не создан.
