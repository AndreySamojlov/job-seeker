# Greenhouse Live — технический проект эпика

Дата:15.10.2026. Статус: утверждён пользователем, включая политику pending update и истечения срока в§5. Продуктовый владелец требований — [Intent](../../greenhouse-live-intent.md). Критическая проверка завершена; открытых продуктовых вопросов нет. Реализация и production-доставка этим утверждением не выполнялись.

## 1. Результат и существующая база

Рабочая Greenhouse-борда читает существующий Job Machine, автоматически обновляется, сохраняет контекст оператора и различает свежие, устаревшие и недоступные данные. Повторно используются репозиторий с согласованным read-only snapshot, расчёты и native UI wheel0.2.0a2. Внешний вид пользователь оценил как приемлемый; агентный browser interaction/viewport smoke остаётся непройденным.

Факты обследования: локальный18767 читает реальные данные;18768 — synthetic fixture. Read-only API при последнем обследовании вернул7829 вакансий за16.09–15.10.2026 для каждого из двух кандидатских контекстов, начальное состояние требует выбрать кандидата. Более ранняя полная сверка охватывала45382 вакансии. Это наблюдения разных выборок/моментов, не неизменные totals. Фит двух кандидатов различается. Сбор новой истории, пересчёт фита и операции конвейера не входят в эпик.

Текущий loader защищён от поздних ответов, но очищает данные при ошибке и не имеет polling/TTL. `mountBoard` при успешном ответе пересоздаёт form/charts/table. `tblColState` сохраняет скрытие/ширины, но `tblEnableSelection` сбрасывает координатное выделение. `mountStage` хранит выбранный главный график внутри instance и предоставляет только destroy. Эти ограничения требуют расширения общих lifecycle API; loading дополнительных JS-файлов не считается переиспользованием механик.

## 2. Архитектура и границы

Job Seeker владеет нормализованным контекстом, проверкой кандидата, SQL, расчётами, временем исходного снимка и диагностикой доступа к источнику. GET всегда пытается получить свежий согласованный результат; сервер не хранит fallback аналитики и не возвращает прошлый отчёт как live.

Cockpit Engine владеет scheduler, loader, памятью текущего снимка, deadline, отображением freshness и согласованным применением данных в native components. Общий движок оперирует нейтральными domain/context/row keys и ничего не знает о Greenhouse SQL или правах submit.

Выбран memory snapshot в рамках одного mount: он сохраняет последнее полное успешное чтение текущего контекста. Не используется localStorage/sessionStorage/IndexedDB/диск, нет межпользовательского server cache. При уходе со страницы/destroy снимки и таймеры освобождаются. Отдельные вкладки независимы. Такой выбор соответствует уже принятой архитектуре и ограничивает хранение кандидатских данных.

Альтернативы: серверный fallback усложнил бы изоляцию и срок хранения, а постоянное browser-хранилище оставляло бы данные после закрытия страницы. Они не нужны для пятиминутной устойчивости открытой борды. SSE/WebSocket не требуются при существующем GET и редкой смене исходных данных; используется ограниченный polling.

## 3. Версионирование и серверный контракт

Изменения распространяются новым immutable wheel после0.2.0a2. Auto-refresh включается явной нейтральной конфигурацией BoardSpec, по умолчанию выключен для прежних потребителей. Старый static mode, MP Cockpit и legacy routes сохраняют поведение; ранее выпущенные wheel не заменяются по прежнему имени/hash. Consumer фиксирует новую совместимую версию и её provenance, без CSS/JS-копий.

JSON остаётся board-v1: серверные `state=live|unavailable` не получают фиктивного stale. Browser view-state строится поверх валидного GET. При включённом polling обязательны дополнительные meta-поля: `context`, `read_id`, `snapshot_at`, `snapshot_age_ms`; `fetched_at` сохраняется как время завершения успешного чтения. В static mode старые payload без новых полей продолжают поддерживаться. Клиент с polling отвергает неполный freshness-контракт и не изобретает возраст.

`context` содержит domain, фактический candidate_id, обе календарные даты, board, availability, page, page_size, sort_key, sort_direction. Значения нормализует сервер; пустые строки приведены к отсутствию фильтра, даты явные. `table.row_key` объявляет стабильную идентичность таблицы; для Greenhouse это vacancy_id. Engine использует объявленный ключ, не предметное имя поля. Внутренний context key строится из канонических пар и сравнивается полностью; нельзя использовать только URL без нормализации или только candidate_id.

Первые resolved defaults разрешены только в bootstrap-ответе текущего поколения: выбранный единственный активный кандидат, диапазон30 календарных дней, default sort/page. Они фиксируются в client params. Полночь Europe/Moscow не сдвигает уже выбранный период: даты видимы и остаются фиксированными до явной смены; при новом открытии страницы defaults рассчитываются заново. Несколько активных кандидатов возвращают selection_required; это экран выбора, не пригодный снимок персональной аналитики. Уже выбранный кандидат не заменяется другим при изменении списка active. После bootstrap следующий ответ обязан совпасть с запрошенным canonical context; несовпадение — отказ установки, а не автоматический переход к чужой выборке.

`read_id` — идентичность серверного чтения, не знак более новой бизнес-записи. Порядок принятия контролируется локальным generation, поэтому несравнимые UUID/timestamps не служат сортировкой конкурентных ответов. Диагностика может хранить read_id, elapsed, counts и outcome, но не DSN, имена кандидатов, вакансии или raw payload.

`snapshot_at` фиксируется при начале согласованного read transaction; текущий fetched_at в конце отчёта не становится временем происхождения данных. `snapshot_age_ms` вычисляется по монотонному времени от начала снимка до формирования ответа. GET держит repeatable-read/read-only и statement_timeout≤10s.

Общий server deadline20s начинается при входе в async GET handler и заканчивается готовностью сериализованного ответа. Он включает admission, daemon status, соединение, SQL, builder и JSON. Для источников выделяется не более15s от входа, оставшиеся5s — резерв обработки/сериализации. Каждый шаг проверяет remaining budget; daemon status≤3s, connect≤5s, каждый SQL≤min(10s, remaining source budget). HTTP transfer не объявляется частью управляемого server deadline; client25s оставляет запас5s, а медленная сеть всё равно может дать корректный timeout.

Admission выполняется неблокирующе в async wrapper **до** отправки работы в sync threadpool. Начальная конфигурация — один процесс приложения, два слота и выделенный bounded executor для report pipeline: только получивший слот запрос попадает в executor, очереди ожидающих аналитических работ нет. При занятых слотах возвращается очищенный503 с Retry-After. Health/static не используют этот executor. Если внешнее ожидание достигло20s, wrapper отвечает503, но слот остаётся занят до фактического завершения worker cleanup. Отмена клиентом также не освобождает слот раньше времени. Это не обещание принудительно остановить произвольный Python-код: SQL ограничен source deadline, CPU builder/serializer проверяются на репрезентативном объёме; после возврата управления просроченный результат отбрасывается. Дальнейшие чтения не накапливаются за зависшим worker. Server shutdown явно закрывает executor и соединения.

Успех, включая total_rows=0, возвращает200/live и no-store. Валидация/недоступный выбранный кандидат —422 со стабильным безопасным кодом, источник/бюджет/admission failure —503. Неподдерживаемые права401/403, invalid context/schema и render failure не маскируются под временную недоступность БД. /healthz отражает процесс и не зависит от PostgreSQL, чтобы отказ данных не перезапускал туннель.

## 4. Scheduler и freshness

Начальная настройка polling —60s после завершения предыдущего запроса, таймаут клиента25s. Один активный запрос и максимум один pending timer на mount. Пользовательская смена контекста начинает новое generation и отменяет старый fetch; старое завершение ничего не устанавливает. Ошибки не вызывают tight retry, следующая попытка идёт по scheduler. Скрытая вкладка не poll-ит; при возвращении выполняются проверка срока и немедленное чтение. Visibility/BFCache transitions и destroy имеют явный lifecycle, без накопления обработчиков.

Возраст в браузере не зависит только от wall clock. Консервативный initial age равен snapshot_age_ms плюс измеренному request RTT; это может истечь раньше, но не омолаживает медленный ответ. Дальше прибавляется elapsed от получения: максимум монотонного elapsed и неотрицательного wall elapsed. Скачок часов вперёд может досрочно скрыть снимок, откат часов не продлевает его; неоднозначность после suspend/BFCache требует свежего чтения, а не сброса возраста. Server timestamp нужен для понятной подписи, не для доверия к локальным часам.

Отдельный expiry timer срабатывает на300000ms effective age независимо от зависшего fetch, ручного взаимодействия и очередного scheduler tick. На visibility return и непосредственно перед render/copy выполняется повторная проверка deadline. Ошибка, repaint, применение pending и повторное чтение того же snapshot из памяти не меняют время его происхождения. Ответ, уже достигший предельного возраста при получении, не устанавливается.

| Событие | Требуемый экран |
|---|---|
| Первое чтение нового контекста | loading/экран выбора, без данных другого контекста |
| Текущее валидное200, включая пустоту | live; последняя успешная выборка заменяется целиком |
| Auto-refresh в полёте при пригодном текущем снимке | остаётся совпадающий отчёт с признаком обновления, без сброса контекста |
| Network/timeout/503 текущего запроса, возраст<300s | stale, предупреждение и исходное время успешного чтения |
| Нет совпадающего снимка или возраст≥300s | unavailable, прежние численные данные и copy/export недоступны |
|422/401/403, несовпадение context или невалидный контракт | очистка персональных данных; явная ошибка выбора/доступа/контракта |
| Успех после ошибки | автоматическое восстановление на том же текущем контексте |
| Позднее завершение старого generation | никаких изменений экрана или сроков |

Смена кандидата, периода, борда, availability, страницы или сортировки инвалидирует fallback прежнего запроса. Для простоты и приватности не ведётся история cache по всем фильтрам. Неудавшаяся новая выборка не возвращает содержимое предыдущей. Статусы браузерного снимка и истории доступности вакансий — разные понятия; stale отчёта не означает закрытую вакансию.

## 5. Применение обновлений и рабочий контекст

Нативные components получают lifecycle для обновления данных и восстановления view-state. Job Seeker не управляет их внутренним DOM. Движок сохраняет выбранный главный график, состояние развернутой диаграммы, горизонтальную прокрутку таблицы, видимый row anchor и offset, hidden/widths/sort, фокус и состояние фильтров. При удалении anchor-row выбирается ближайшая доступная позиция, без скрытого возврата на начало. Явный переход страницы/фильтра может менять содержимое и сбрасывать неподходящий row anchor, но не ширины колонок.

Форма фильтров reconciles по ключам; poll не пересоздаёт активный input. Колонки reconciles по key. Набор строк имеет стабильный объявленный row_key, а не только DOM-индекс. Перед commit проверяются наличие, непустота и уникальность row keys в странице; нарушение не допускает восстановления anchor/selection и установки отчёта. Изменение значений таблицы, KPI и charts принимается как одно read generation: нельзя обновить карточки сейчас, а старую таблицу оставить выглядящей частью того же снимка. До commit валидируются все структуры; ошибочный render не оставляет смешанные данные под live. Если восстановить предыдущее согласованное отображение безопасно невозможно, показывается render-error/unavailable.

**Принятая политика:** во время pointer drag/resize, открытого column menu, редактирования фильтра, выделенного диапазона таблицы или открытой chart modal новый snapshot не перерисовывает отчёт. Хранится только последний валидный pending snapshot текущего generation; показываются исходное время видимого отчёта и «Есть новые данные». После короткого жеста/закрытия меню либо modal pending применяется автоматически; сохраняющееся выделение требует явной кнопки «Применить обновление», предупреждающей о сбросе выделения. Уже скопированное не изменяется задним числом. Политика принята пользователем.

Откладывание не отменяет300s границу видимого снимка. При её истечении старые значения, ссылки на row objects, координаты selection и copy/export инвалидируются; menu/modal старого снимка закрываются и освобождаются их interaction tokens. События от прежнего lifecycle больше не действуют на новый view. Если есть подходящий pending моложе300s, он устанавливается автоматически после этой инвалидации: это уже безопасное восстановление, а не замена значений под существующим выделением. Если последний source attempt был неудачным, установленный pending остаётся stale с исходным временем; иначе live. Если пригодного pending нет, экран unavailable, и следующий валидный успех устанавливается автоматически без ожидания исчезнувшего выделения. Эта явная граница срока принята пользователем как часть политики§5.

Pending age не обнуляется в момент применения. Один видимый и один pending snapshot — верхняя граница хранения, новые pending заменяют старый. Смена контекста/destroy очищает оба. Кнопка применения, статус waiting update и freshness renderer принадлежат движку, не consumer.

Native CSV остаётся честным экспортом загруженной страницы с явной подписью. Фильтрация полной выборки выполняется на серверном контексте через rail; page-local table filters не включаются как замена. Browser test должен проверять настоящие resize/copy/sort/hide, а не наличие JS в HTML.

## 6. Совместимость данных и ограничения

Все действующие семантические ограничения сохраняются: source/ats_family Greenhouse, board token из допустимого API source_url, LEFT JOIN одного candidate_id по уникальной паре,0-fit≠NULL, versioned rubric, whole-selection aggregates и100-row server page. Unknown availability и срок жизни не заменяются нулями. Начальный диапазон30 дней остаётся явно видимым и не переключается на всю историю из-за пустоты.

Истечение TTL не требует server migration. Дополнительные metadata/row identity добавляются к существующему consumer payload; нужны контрактные tests на старый static и новый polling modes. Полные arrays диаграмм не молча сэмплируются; ресурсный риск проверяется на репрезентативном полном объёме, включая много оценённых вакансий. Если бюджет не достигается, требуется адресная оптимизация/явное согласование изменения представления, а не скрытый cap.

## 7. Рабочее размещение и доставка

Целевое размещение наследуется из принятой архитектуры: отдельное приложение на lab-do с loopback публикацией и именованным web-туннелем существующего демона. В локальной проверке используется уже разрешённый DB-туннель; его credential не переносится на сервер. Сервер получает отдельную минимальную роль чтения необходимых таблиц и отдельный secret injection. Создание роли/выдача доступа, новый сервис и применение registry требуют определённого задания на доставку; этот проект не выполняет их.

До доставки агент read-only проверяет актуальные ресурсы lab-do, пути/порты, сети, доступность образа/отката и свойства registry reload работающего демона. Историческое заполнение диска96% не считается текущим фактом. Сборка выполняется вне ограниченного сервера, если бюджет этого требует. Отказ БД не меняет desired туннеля; намеренно остановленный туннель не запускается автоматически. Registry не применяется без учёта прерывания других соединений. Workers, их images/volumes и Observer не заменяются ради борды.

Откат возвращает предыдущие wheel/приложение/образ и конфигурацию борды, не откатывая бизнес-данные. Новая публикация не становится публичным multi-user сервисом: текущая проверка active candidate не является системой многопользовательской авторизации.

## 9. Готовность к следующим стадиям

Общая архитектура, memory snapshot и политика§5 утверждены пользователем. Designing, Brainstorming и Grill Me завершены для этого замысла. Staging и единственная декомпозиция записаны в [Decomposition Map](../../decomposition-map.md): A — проверенная локальная борда, B — целевое размещение lab-do.
