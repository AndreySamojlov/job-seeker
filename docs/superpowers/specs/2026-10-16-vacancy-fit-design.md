# Оценка соответствия кандидата вакансии через Jev

Дата: 16 октября 2026. Статус: проект Brainstorming принят пользователем; продуктовые уточнения Grill Me приняты. Реализация не начата. Основание — [Epic Intent](../../vacancy-fit-intent.md). Рубрика, однократность, правила неизвестного и отображение согласованы. Staging и текущий маршрут — в единой [Decomposition Map](../../decomposition-map.md).

## Границы

Новый оценщик выдаёт одно целое число 0–100 для пары candidate_id/vacancy_id. Jev целостно оценивает требования по подтверждённым фактам; опорные значения 0/25/50/75/100 и переносимый опыт определены в Intent. Неизвестное снижает число. Установленное нарушение обязательного требования даёт 0. Только число выводится в борде.

Существующий triage и его маршрутизация сохраняются. Новая оценка не должна зависеть от прохождения кандидатских role/geo/company gates: иначе часть новых вакансий не получила бы обещанный fit. Автоматические отклики и production-доставка не входят в эту работу.

## Источники и точка запуска

В существующем `discovery.store.upsert_vacancy` реальная вставка отличается от дубликата и сопровождается `vacancy.discovered`; `discovered_at` задаётся БД. Это предложенная граница новой вакансии: повторное обнаружение canonical_url не создаёт новую оценку.

Предлагается в одной транзакции с новой вакансией фиксировать задания для активных на этот момент кандидатов. Включение функции имеет явную границу; существующие строки не перебираются для заполнения. Активация кандидата действует для последующих вставок, а не исторических вакансий. Нужна проверка всех путей создания нормализованных вакансий; Telegram lead сам по себе ещё не vacancy.

Уточнение Grill Me: деактивация не отменяет уже созданные задания и их технические повторы. Проверка текущего active не должна блокировать завершение ранее назначенной пары; active ограничивает только создание заданий для новых вакансий.

Сейчас у candidate есть active и created_at, но это не журнал повторных активаций. Предложенная транзакционная фиксация получателей в момент поступления устраняет необходимость восстанавливать прежнее значение active из текущей строки. Пограничную конкурентную активацию следует упорядочить блокировкой или эквивалентной сериализацией в путях записи.

## Данные и ответственность

Отдельный модуль оценки владеет заданиями, подготовкой входа, вызовом Jev и сохранением результата. `triage_result.fit_score` не перезаписывается. Предлагается отдельная запись на пару с уникальным ключом, состоянием задания, номером попытки, сроком аренды, next_attempt_at и nullable целым score с ограничением 0–100.

Происхождение содержит точную версию модели, версию рубрики, версии или hashes исходных фактов и текста вакансии, время подготовки и завершения. Эти сведения нужны диагностике и не добавляют пояснений в пользовательский интерфейс. Секрет API хранится вне Git; raw payloads и факты кандидатов не попадают в обычные логи и audit evidence.

Получение текста вакансии использует существующие ATS-клиенты без кандидатских фильтров. Подтверждённые факты собираются из канонических кандидатских источников; предпочтения поиска не подмешиваются. Ошибка получения текста или чтения фактов — техническая ошибка, а не доказательство отсутствия требований или опыта.

## Неизменность и повтор

Предложенные состояния: pending → processing → completed; временный сбой возвращает задание в retry_wait, истёкшая аренда допускает повтор. Финальное число записывается атомарно один раз. Поздний ответ старой попытки не перезаписывает результат новой; разные workers не получают право завершить одну пару одновременно.

Пользователь выбрал фиксацию исходного входа перед первой попыткой. Снимок находится в защищённом рабочем хранилище, вне Git и обычных логов; технические повторы оценивают те же данные независимо от последующих изменений профиля или вакансии. После completed задания не создаются повторно при изменении профиля, вакансии или модели.

Timeout, 429 и временные 5xx повторяются с ограниченной частотой и backoff; число не подставляется до успеха. Ошибки ключа, доступа, схемы и постоянные 4xx должны быть видны агенту как требующие исправления, без бесконечного быстрого повтора. Сохранённое незавершённое задание можно продолжить после исправления причины; это не пересчёт завершённой оценки. При сбое весь конвейер не должен останавливаться.

## Контракт Jev

Адаптер переводит согласованную рубрику в поддерживаемый Score-контракт и возвращает проверенное целое число. Подтверждение обязательного нарушения выделяется в отдельный типизированный ответ; итог 0 имеет приоритет над остальной оценкой. Отсутствие факта не трактуется как установленное нарушение.

Уточнение Grill Me: отсутствие явно обязательного опыта Java при установленном факте «нет опыта Java» даёт 0 даже при переносимом опыте C#. Само отсутствие упоминания Java — неизвестность, а не установленное нарушение. Обязательное требование имеет приоритет, переносимый опыт не переименовывается в конкретный неподтверждённый навык.

До реализации нужно сверить действующую схему Score, нормализацию шкалы, фиксированный model ID, лимиты и обработку ошибок по официальной документации. Вероятность Noul не превращается умножением на 100 в итоговый fit. Структурная валидность не заменяет проверки качества. Текст вакансии считается данными и не должен менять инструкцию оценщика.

Проверка документации 16.10.2026: [Score](https://docs.typesafe.ai/primitives/score) принимает 2–10 текстовых уровней и возвращает позицию 0..N−1, включая дробные значения. Наши пять уровней дают 0..4; нормализация — умножение на 25 и округление половины вверх до целого. Значения вне диапазона, bool, NaN и бесконечность отвергаются, а не обрезаются. [Choice](https://docs.typesafe.ai/primitives/choice) возвращает выбранный именованный вариант. Для обязательного нарушения используются три взаимоисключающих состояния: `confirmed_violation`, `no_confirmed_violation`, `unknown`; только первое принудительно даёт 0. Это вывод модели, не детерминированное доказательство истины, поэтому проверяется на размеченных примерах.

Прямой HTTP-вызов использует уже имеющийся httpx, без нового SDK и изменения lock. Начальная закреплённая версия — `jev-1.13.0`, стабильный ID из [Models](https://docs.typesafe.ai/models), без движущегося alias. При недоступности ID у аккаунта задание блокируется с диагностикой; незаметного переключения модели нет. Запрос использует один state и два вопроса: Score и Choice. Полный payload вместе с инструкциями, model ID и rubric version фиксируется до вызова; повторы отправляют те же данные. Ключ не включается в снимок.

Для первой Story вход поставляется как явно типизированный набор фактов с идентификаторами происхождения и статусами, без чтения production. Автоматическое извлечение всех канонических фактов, ATS fetch и постановка новых пар принадлежат S2. Неизвестный или approximate статус не повышается до verified. S1 не объявляется готовностью полного охвата фактов S2.

## Борда

Кандидатский LEFT JOIN получает только новую оценку. NULL рендерится как «—», 0 сохраняется как число. Старый fit не используется как fallback и не выводится второй колонкой. Графики и агрегаты фита также не должны незаметно продолжать показывать `fit-2`.

Пользователь выбрал заменить диаграмму A/B/C/D числовым распределением Jev 0–100. Предлагается частотный ряд по целым значениям, без новых категорий или бэндов. Неоценённые исторические вакансии учитываются отдельно, не попадают в столбец нулевого соответствия. Остальные графики фита получают только значения Jev; текущие фильтры и candidate scoping едины с таблицей.

Пользователь выбрал фронтенд-сортировку всей выбранной совокупности с последующей клиентской пагинацией. Текущий `board.repository` сортирует в SQL и возвращает страницы по 100 строк; этот контракт потребуется изменить.

Предлагается получать полный выбранный набор частями из одного согласованного снимка с идентификатором, числом строк и контекстом кандидата/фильтров. Технический порядок передачи по стабильной идентичности не является пользовательской сортировкой. Фронтенд применяет выбранную сортировку ко всему набору, после чего выделяет страницу. Частично загруженный набор нельзя выдавать за полностью отсортированную выборку. Изменение фильтра или кандидата отменяет старую загрузку; ответы разных снимков не смешиваются. Повторное обновление заменяет набор целиком после завершения загрузки и сохраняет пользовательскую сортировку.

Снятие LIMIT в одном неограниченном запросе не предлагается. Размер частей, срок хранения снимка, лимиты памяти и времени требуют расчёта при технической детализации; достижение предела должно давать явный отказ загрузки, а не незаметное усечение. Контракт согласованного чтения и действующие правила свежести Greenhouse Live сохраняются; долгую загрузку нельзя считать свежей только по моменту получения последней части.

## Проверка

Synthetic fixtures покрывают рубрику, неизвестное, переносимый опыт, обязательное несоответствие и prompt injection в вакансии. Проверки жизненного цикла покрывают дубликаты, границу включения, активацию, отсутствие backfill, сбои, повтор, истечение аренды, конкурентное завершение и запрет перезаписи completed. Проверки борды покрывают candidate scoping, 0 против NULL, отсутствие старого fallback, графики и выбранную семантику сортировки.

DB-проверки разрешены только в защищённом recovery-кластере 25439/job_machine_recovery_test. Production не используется для тестовых записей. Реальные внешние вызовы и применимость условий хранения Jev проверяются отдельно от synthetic tests. До заявления готовности нужны baseline unit/smoke и релевантные интеграционные проверки, review и обновление FACT по смысловым владельцам.

## Граница этапа и последующие проверки

Граница сортировки согласована: вся выбранная совокупность на фронтенде. Диаграмма категорий заменяется числовым распределением Jev. Технические повторы используют исходный зафиксированный вход. Пользователь принял проект Brainstorming и переход к Grill Me 16 октября 2026.

Критическая проверка закрыла две продуктовые границы: обязательная технология имеет приоритет над переносимостью при установленном отсутствии опыта; после деактивации уже созданные задания завершаются. Оба ответа пользователя сохранены в Intent.

Необратимость оценок по неполным данным следует из согласованной однократности. Ресурсная стоимость всей выборки и условия хранения у провайдера остаются инженерными проверками до реализации соответствующих частей, а не фактами подтверждённой готовности. Техническая детализация должна установить ограничения snapshot-загрузки, точный API Jev, ресурсные бюджеты и повторяемую проверку качества. Если проверки потребуют изменения принятого замысла, соответствующая ветка возвращается в Brainstorming и Grill Me.

После завершения Brainstorming обязательны Grill Me, Staging и Decomposing перед планом реализации. Этот проект не означает разрешения на миграции или redeploy production.
