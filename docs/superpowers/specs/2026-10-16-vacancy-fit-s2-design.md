# Jev S2 — автоматическое назначение для новых подтверждённых вакансий

Дата: 16 октября 2026. Статус: локальная Story S2 реализована и проверена; production-доставка не выполнялась. Родитель — [Epic Intent](../../vacancy-fit-intent.md); общий контракт Jev — [проект Epic/S1](2026-10-16-vacancy-fit-design.md); текущая декомпозиция — [единая карта](../../decomposition-map.md), evidence — [audit S2](../../audit/vacancy-fit-s2.md).

## Результат

Каждая вакансия, впервые успешно прошедшая verify после включения S2, один раз назначается всем кандидатам, активным в момент verify. Подготовительная очередь получает текст вакансии и факты каждого назначенного кандидата, затем вызывает существующий immutable worker S1. Готовые и ошибочные задания остаются наблюдаемыми; отсутствие оценки не подменяется нулём.

## Поток данных

1. DB trigger на таблице `vacancy` фиксирует назначения при новом `INSERT` со статусом `verified` или первом переходе из другого статуса в `verified`. В одной PostgreSQL-транзакции создаётся уникальная запись `fit_prepare` для `vacancy_id` и дочерние пары `candidate_id/vacancy_id` для активных кандидатов. Это покрывает стандартный `discovery.store.mark_verified` и прямые записи ручных источников. Исторические verified строки при установке trigger не сканируются. Фиксация выполняется именно на успешном verify: кандидат, активированный после обнаружения, но до verify, включается; выключенный к этому моменту исключён.
2. Создание `fit_prepare` не вызывает ATS или Jev. Внешний fetch и подготовка проходят асинхронно вне короткой транзакции. При успешном verify с нулём активных кандидатов уникальная запись сразу завершена без fetch; поздняя активация и повторный verify не создают backfill.
3. Подготовительный worker забирает одну запись с lease/SKIP LOCKED, получает `description` существующим ATS-клиентом и нормализует HTML тем же чистым `triage.htmltext.strip_html`, без triage-гейтов; текст сохраняется в рабочей БД для восстановления. Если источник предоставляет только excerpt (сейчас такой контракт явно задокументирован для Himalayas), используется excerpt. Для каждого закреплённого кандидата worker загружает факты и вызывает `fit.store.create_job`; эта операция сохраняет полный payload по уже согласованному контракту S1 перед первым вызовом Jev. Перезапуск после сбоя повторяет `create_job` идемпотентно.
4. После успешного создания всех пар подготовительная запись завершается. Независимый Jev worker исполняет созданные `fit_job` и сохраняет результат по существующим правилам аренды/повтора S1. Деактивация после verify не удаляет пару и не блокирует её завершение.

## Источники и фильтры

- Claims: текст, id, исходный статус, proof и ограничения использования. Статус не повышается.
- Experience Cloud: позиции, достижения и навыки с evidence/claims и `safe_use`; точность/приблизительность переносится в `FitFact.status`.
- Answer vault: только `locked` и только поле, нормализованное имя которого находится в явном allowlist квалификационных ответов. Контакты, согласия (`optional-policy`), заблокированные ответы, неизвестные поля и непроверенные категории исключаются. Новый allowlist — конфигурационный whitelist; отсутствие поля означает skip. В тестах используются синтетические поля, без чтения значений локального или production vault.
- Search profile и предпочтения пользователя не читаются. Имя кандидата не передаётся. Текст вакансии получает соответствующий `ATS family` клиент, не triage-кандидатный фильтр.

## Состояния, повторы и наблюдаемость

`fit_prepare` имеет уникальность по вакансии, состояние `pending/processing/retry_wait/blocked/completed`, попытки, next-attempt, lease и безопасный `last_error_code`. Дочерняя пара уникальна по candidate/vacancy и хранит свой прогресс создания S1 задания. Lease покрывает максимальный ограниченный ATS retry window: 3 запроса с timeout 15 секунд и до двух Retry-After ожиданий по 120 секунд (285 секунд); используется 360 секунд и продлевается перед подготовкой каждого кандидата. Ограничения уникальности, lease fencing и запрет сырого payload в логах обязательны.

Временная сетевая ошибка, timeout, 429 и 5xx переводят подготовку в retry с backoff; существующий discovery/verify уже зафиксирован и не откатывается. Постоянный 4xx, отсутствующее содержимое после успешного запроса, превышение безопасного размера или ошибка контракта блокирует подготовку с очищенным кодом; некорректные canonical facts (Pydantic validation failure) классифицируются как permanent. Неожиданные ошибки fit-стадий в pipeline выводят только фиксированный код `operation_failed`, без traceback или текста исключения. После устранения причины операторская CLI-команда возобновляет только blocked preparation, не меняя уже сохранённые входы или completed пары. Ошибка записи самой связки verified + recipient snapshot откатывает её общую транзакцию: назначение не должно потеряться.

Штатный периодический `pipeline.auto.run_auto_cycle` запускает ограниченную обработку `fit_prepare` после verify и до triage, затем ограниченную обработку созданных заданий существующим Jev worker. Очереди подбираются на каждом цикле, а не только для вакансий, подтверждённых в этом конкретном цикле: поэтому ручной INSERT/UPDATE тоже будет обработан при следующем запуске цикла. Исчерпание batch limit оставляет остаток в durable queue следующему циклу, без молчаливого удаления. Ошибки этих стадий изолированы от последующих pipeline stages. Отдельные MCP-вызовы verify создают назначения тем же DB trigger; сами по себе они не вызывают внешние сервисы, очередь обработает следующий периодический auto cycle. Фактический scheduler/production credentials/runtime deployment проверяются отдельно в S4.

## Идемпотентность и конкурентность

- Конфликт canonical URL при discovery не создаёт новую vacancy и не назначает fit.
- `fit_prepare.vacancy_id` уникален; дочерняя пара имеет уникальность candidate/vacancy. Повторный verify/worker после commit не удваивает работу.
- Trigger на `vacancy` и DB trigger на `candidate.active` используют общий transaction-scoped advisory lock, включая прямые INSERT/UPDATE в обход приложения. Снимок active-set выполняется после получения lock. Так одновременная активация/деактивация строго упорядочивается до или после verify-снимка; блокировка только уже активных строк недостаточна, потому что не защищает строки неактивных кандидатов от конкурентной активации. Сетевых вызовов под этим lock нет. DB tests фиксируют линейный порядок verify/activation/deactivation.
- HTTP выполняется только после фиксации lease; состояние задания и вход сохраняются до внешнего вызова. Lease/token fencing и immutable result остаются на стороне S1.
- Два prep workers не получают одну lease. Падение между созданием `fit_job` и обновлением child status безопасно: повторный `create_job` не меняет payload, после чего очередь может отметить пару готовой.

## Границы

S2 — локальный срез A. Он не вызывает Jev в транзакции discovery, не меняет eligibility/triage, не влияет на pipeline routing и не возвращает пользовательскую оценку. UI и полная сортировка — S3. Реальные данные кандидатов, миграция production, настройка production key, redeploy и включение функции в lab-do — S4 с отдельным определённым заданием. Обновление очереди не backfill-ит уже verified строки.

## Проверка

Synthetic tests должны доказать: ровно одно назначение после first verify; ни одного на duplicate discovery; активные кандидаты фиксируются на verify, включая активацию между discovery и verify; пустая выборка не приводит к позднему backfill; деактивация после verify не отменяет пару; конкурентные verify/activation/deactivation сохраняют уникальность; fetch content один раз на вакансию и excerpt используется; разделение нескольких кандидатов; allowlist включает только locked разрешённые поля и отсекает контакт/consent/search preference/unknown; no-content и постоянная ошибка видны как blocked; transient ошибки повторяются; crash после S1 create_job повторяем; подготовительная ошибка не откатывает vacancy verification и не блокирует другие pipeline stages.

Проверки запускаются только на synthetic candidate/vacancy и recovery-кластере 25439/job_machine_recovery_test. Внешний Jev для проверки S2 может получать только synthetic payload. No production DB, real candidate facts, live worker interruption, migration, redeploy или реальная форма подачи.
