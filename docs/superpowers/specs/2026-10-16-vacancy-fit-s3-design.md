# Jev S3 — отображение оценки в Greenhouse-борде

Дата: 16 октября 2026. Статус: спецификация одобрена пользователем; локальная реализация S3 готовится к закрытию. Родитель — [Epic Intent](../../vacancy-fit-intent.md), согласованный общий проект — [Jev design](2026-10-16-vacancy-fit-design.md), декомпозиция — [карта](../../decomposition-map.md). Production-доставка остаётся в S4.

## Результат и границы

Для выбранного активного кандидата Greenhouse-борда показывает только Jev score из `fit_job`. Историческое отсутствие результата и незавершённые/заблокированные задания показываются как «—», завершённый score `0` — как `0`. Старый `triage_result.fit_score`, band и rubric не участвуют в строках, фильтрах и диаграммах Jev. Условия новой оценки остаются у S1/S2; S3 не инициирует пересчёт и не меняет triage, eligibility или submit.

Числовое распределение включает завершённые Jev scores по целым значениям 0–100; NULL учитывается отдельным числом «Не оценено». Весь набор выбранного кандидата, периода, борда и колонковых фильтров загружается в одном repeatable-read/read-only снимке, затем браузер применяет выбранную сортировку и разбивает результат на страницы. SQL-порядок транспортного набора детерминирован и не является сортировкой интерфейса. UI не отображает и не позволяет выгрузить частичный набор как полный.

Срез остаётся локальным A. Production migration, подключение real candidate facts, redeploy, обновление production-доски и реальное выполнение Jev отложены до S4 и отдельного задания. Используются существующий локальный read-only доступ и только текущие production-доступные данные в read-only проверке; DB/browser tests работают на synthetic/recovery-контуре.

## Источник и согласованность

В пределах транзакции `REPEATABLE READ READ ONLY` repository выбирает Greenhouse vacancies и `LEFT JOIN fit_job` по выбранному `candidate_id` и `vacancy_id`. Присоединяется один уникальный результат пары; score разрешён только при `status='completed'`, иначе `NULL`. Передача результата содержит только поля борды: идентификатор вакансии, заголовок, URL, компания, локация, режим работы, дата обнаружения, токен борда и nullable Jev score. Payload, факты кандидата, провайдерские ответы, модель, рубрика и пояснения не выдаются UI.

Кандидат выбирается тем же правилом, что сейчас: при единственном active candidate он выбирается автоматически, при нескольких обязателен явный выбор. Изменение кандидата или фильтра создаёт новый canonical context и полностью заменяет предыдущий набор. Снимок, KPI, диаграммы и таблица получаются из одной транзакционной версии данных.

## Полный набор и ресурсы

Ответ содержит все строки выбранного фильтра до браузерной сортировки и pagination. Ограничители — `MAX_ROWS=100000`, сериализованный UTF-8 JSON `MAX_RESPONSE_BYTES=32 MiB`, источник не более 15 секунд, весь ответ не более 20 секунд. Проверка строки/байтов выполняется до публикации результата. Превышение любого лимита переводит весь ответ в `unavailable` с безопасным стабильным кодом (`snapshot_too_large` или существующий код timeout); частичный payload запрещён. Значения лимитов вынесены в один модуль и покрываются проверками границ. Если обычная выбранная совокупность упирается в лимит, лимит должен быть скорректирован по измеренным безопасным данным до закрытия S3, сохраняя отказ вместо усечения.

Текущий `cockpit-engine==0.2.0a5` таблицу сортирует через новый серверный запрос, а `renderBoardTable` отрисовывает все строки, которые получил. Для S3 требуется согласованная адаптация двух browser assets wheel: runtime получает полный массив строк и сохраняет серверный sort/page режим для остальных борд; Job Seeker включает явный client-side режим, в котором таблица сортирует весь массив стабильным `vacancy_id`, применяет slice страницы по 100 строк и экспортирует текущую страницу. Колонковые фильтры остаются частью запроса полного снимка, чтобы серверные агрегаты и строки имели один набор. Фильтр запускает новый полный snapshot, сортировка и переключение страниц — нет.

Браузер ограничен одним применённым полным снимком на отчёт. В процессе загрузки старые ответы не смешиваются с новым контекстом; ошибка не заменяет состояние успешного снимка неполными строками. Пользовательская сортировка сохраняется при refresh; страница сбрасывается при смене candidate/filters. Клиентская сортировка сравнивает числа как числа, строки — детерминированно, NULL сортирует последним в обоих направлениях, score `0` остаётся числом. UI отображает текущую страницу, а сортировка и пагинация применяются ко всему загруженному набору.

## Представление

- Единственная колонка fit содержит `JeV`-оценку целым числом или `—`; прочие продуктовые колонки сохраняют текущие labels и безопасные ссылки.
- Числовая диаграмма показывает частоты по score, без A/B/C/D и без объединения разных Jev-значений в категории. Неоценённые записи указаны отдельно и не входят в score 0.
- Колонковые фильтры фильтруют полный набор до клиентской сортировки и пагинации; агрегаты согласованы с выбранным фильтром согласно текущему board contract.
- Контекст кандидата, дат, борда и колонковых фильтров входит в canonical context/read identity. Смена контекста отменяет/отбрасывает поздний результат.
- Ошибка чтения, превышение лимита и успешная пустая выборка различимы; успешная пустота остаётся `live`.

## Проверка

Synthetic unit/DB проверки подтверждают JOIN-контракт и scoping, completed-only score, отсутствие legacy fallback, 0/NULL, числовое распределение, полный snapshot, стабильные NULL/ID ordering и границы row/bytes/time. Wheel/runtime tests проверяют opt-in client mode, сортировку до slice, sort persistence и неизменность server mode; ASGI и запущенный HTTP fixture подтверждают полный набор из 201 строки. Пользователь визуально принял synthetic board: колонку Jev, различие `0`/`—`, числовое распределение и pager. Поздние ответы покрыты штатным refresh controller, но отдельный браузерный визуальный сценарий агентом не выполнялся.

Recovery DB проверяет SQL контракт на локальном PostgreSQL 25439/job_machine_recovery_test с synthetic данными. Baseline unit/smoke выполняются по AGENTS.md. Отдельная read-only локальная сверка может подтвердить наличие/отсутствие `fit_job` и производительность на существующей схеме; она не заменяет DB/browser regression и не запускает worker. После изменений выполняется независимый review и обновляются Functional Specification, decomposition map и evidence владельцами соответствующих фактов.

## Приёмка S3

S3 завершена, когда локальная борда получает Jev из `fit_job`, никакая старая оценка не подставляется, 0 и NULL различаются, числовое распределение соответствует выбранному полному набору, адаптированная таблица сортирует до page slice на synthetic наборе больше страницы, согласованный ответ не смешивает контексты, лимиты приводят к явному отказу, и весь результат прошёл релевантные проверки/review. Изменение bundled wheel фиксируется как adaptation с исходным и результирующим hash в provenance. S3 не означает production-доставку.
