# RWR.S1 — технический проект оценки международной удалёнки

Дата: 16 октября 2026. Уровень: Story technical design. Статус: утверждён; уточнённая граница интеграции включена в implementation plan. Родительский замысел: [Epic Intent](../../remote-work-readiness-intent.md); декомпозиция: [RWR](../../decomposition-map.md).

## Цель и граница S1

Показать, что для одной вакансии локально можно сформировать неизменяемый снимок входа, вызвать Jev через Rules Cockpit, получить и сохранить его индекс и версии. Rules не оценивает и не корректирует ответ. Существующий candidate fit (`fit_job`, rubric `jfit-1`) остаётся отдельным контуром.

В S1 входят контракт одной оценки, локальное хранилище, обработка Jev-ответа и защищённая CLI/worker-точка входа для synthetic вакансии. Отображение в борде относится к RWR.S2; автоматическая обработка и актуальная проверка всех вакансий — RWR.S3; production schema/deploy — RWR.S4 и отдельное задание.

## Наблюдаемые факты и ограничения

- Job Seeker использует Cockpit Engine `0.2.0a6` из `vendor/cockpit_engine-0.2.0a6-py3-none-any.whl` согласно `pyproject.toml`. Этот Rules evaluator формирует AST-сигналы и вызывает `attach_scores`; готового Jev-вызова в нем нет.
- Существующий `job_machine.fit` применяет Jev `Score` с candidate facts, а затем преобразует оценку в целое 0–100. Его модель, payload, таблица и семантика не подходят vacancy-only индексу. Повторное использование/изменение `fit_job` смешало бы оценки.
- TypeSafe System One API документирует Noul как вероятность ответа «да» в диапазоне 0–1; `Score` принимает максимум десять уровней. Поэтому для этой оценки выбран Noul, а не преобразование ограниченной шкалы Score. Источник контракта: [TypeSafe OpenAPI](https://api.typesafe.ai/openapi.json).
- Исходник, использованный для кода wheel `0.2.0a6`, найден в чистом worktree `C:\Users\samoj\.codex\worktrees\portable-board-s1\Cockpit Engine`, commit `fe842546f712417ccc3d418b4e5d99f53ebba922`; все `.py` и package files совпадают, кроме двух JS board assets, происхождение которых отдельно закреплено в `provenance/board-s1.json`. Сохранённый проект `Documents\ChatGPT\Cockpit Engine` имеет незакоммиченные изменения пользователя; менять его нельзя. Vendored wheel нельзя редактировать на месте: при изменении зависимости нужен новый immutable wheel и запись provenance/hash по правилам проекта.

## Решение по архитектуре

Добавить в Cockpit Rules типизированную generic точку вызова внешнего decision handler из конфигурации Rules. Rules выбирает и вызывает зарегистрированный handler, передаёт ему вход и возвращает его ответ без изменения; generic Engine не знает TypeSafe URL, ключ, модель Jev или формат Noul и не содержит Job Seeker ветвлений. В Job Seeker регистрируется handler `jev`, который выполняет Jev-вызов. Версионированная Noul-рубрика хранится как конфигурация Rules; в Engine она является данными, не исполняемой оценочной логикой. Не вызывать AST `attach_scores`, не менять ответ, confidence, шкалу или пороги и не принимать решения по вакансии.

В Job Seeker добавляется изолированный модуль `job_machine.remote_readiness` по примеру надёжности существующего Jev worker (короткие DB-транзакции, lease fencing, безопасные диагностические коды, bounded retry), но с собственными типами, таблицей и handler для Rules API. Это не candidate pair и не использует `FitInput`, facts, `FitResult` или `fit_job`.

### Поток одной оценки

1. Caller передаёт идентификатор вакансии и canonical `work_mode`. Явный `onsite` отклоняется до назначения Jev; `remote`, `hybrid` и `unknown` допускаются. S1 caller не делает live-проверку вакансии; S3 назначает оценки только после подтверждённого active/verified состояния.
2. Подготовитель создаёт один immutable snapshot: vacancy ID, исходный текст объявления, канонический hash, pinned model ID и rubric version. Candidate facts, профиль/предпочтения, триаж, резюме, личные данные кандидата и выводы о праве на работу не включаются.
3. Worker claim-ит задание короткой транзакцией, фиксирует её до HTTP и вызывает Jev только через Cockpit Rules passthrough. Jev получает текст объявления и версионированный Noul-вопрос. Рубрика оценивает наличие явных свидетельств поддержки постоянной работы из-за рубежа. `Remote Europe` трактуется как включающее Албанию; `EU only` не включает Албанию; запрет одной группы не равен полному запрету, если объявление явно допускает другие иностранные страны. Неуказанные условия снижают индекс, но не считаются подтверждённым запретом. On-site не получает результата.
4. Rules передаёт сырой Noul answer неизменённым. Job Seeker валидирует форму, диапазон `0 <= n <= 1` и точный model ID, затем сохраняет `n` как Jev fraction без округления/пересчёта. Это проверка целостности контракта, не оценочная логика.
5. Завершение сохраняет использованные model/rubric версии атомарно с исходным Jev fraction. Борда последующего среза форматирует fraction × 100 как процент с одним десятичным знаком; Rules и сохранённый индекс остаются неизменны.

### Noul-вопрос и рубрика

Одна агрегирующая Noul-оценка: «Насколько текст этого объявления указывает, что работодатель готов к постоянной работе сотрудника, физически находящегося за пределами страны/региона найма?». Подробные критерии `true`/`false` и обработка перечисленных географических примеров составляют версионированную рубрику `rwr-1` в каталоге Rules. Текст вакансии трактуется как недоверенные данные; команды, найденные внутри него, не исполняются и не меняют инструкцию.

Исходный Noul value — информационный индекс, а не измеренная частота трудоустройства и не гарантия конкретного работодателя. У него нет отдельного `confidence` поля. Не создавать вторую метрику confidence и не домножать индекс на предполагаемую уверенность.

Начальная модель фиксируется на уже используемой интеграцией модели Jev `jev-1.13.0`, если она доступна для RWR в подключённом аккаунте при реализации; ответ проверяется по фактическому имени модели. Модель или рубрика не меняются автоматически; каждое обновление требует новой версии и не пересчитывает завершённые оценки.

### Данные и повторяемость

Создать отдельную таблицу `remote_work_readiness_job` с ключом `vacancy_id` (одна оценка на вакансию), состояниями `pending`, `processing`, `retry_wait`, `blocked`, `completed`, сохранёнными payload/hash, `model`, `rubric_version`, nullable `jev_value`, attempts/lease/retry/error code и timestamps. Допустимый `jev_value` — только конечное число в `[0,1]`; completed требует значение и versions, незавершённое состояние не содержит результата. Snapshot и completed-результат неизменяемы; повторное назначение конфликтует без перезаписи. Сбой API, невалидный ответ, missing key или потеря lease не становятся нулём.

Перезапуск продолжает исходный payload; retry не пересоздаёт вход. Сетевые/429/5xx ошибки получают ограниченный backoff; постоянные ошибки блокируются и возобновляются явной командой. Неопределённый исход внешнего Jev-вызова разрешает повтор только по политике RWR worker и тому же snapshot; completed всегда защищён от повторного вызова.

Сохранять raw response, prompts, payload и текст объявления в логах запрещено. В обычной диагностике допустимы vacancy ID, состояние, число попыток, model/rubric версии и очищенный код ошибки. Текст объявления уже является предметными данными Job Machine и в Jev отправляется только для соответствующей оценки.

## Варианты и причины выбора

1. **AST/весовые Rules Cockpit.** Не подходит: Rules тогда формировали бы оценку, вопреки согласованному владельцу Jev.
2. **Вызов Jev напрямую из Job Seeker.** Не подходит: обходил бы выбранную пользователем систему Rules.
3. **Rules passthrough к Jev Noul (выбрано).** Сохраняет Rules как обязательную точку вызова, оставляет оценку у Jev и использует native `[0,1]` value, не вводя lossy mapping из Score уровней.

## Риски и условия допуска к реализации

- Добавление passthrough в существующий Engine может не соответствовать его текущей модели AST/catalog/action. До кода проверить исходный Cockpit Engine, найти каноническую точку расширения Rules и спроектировать API совместимо с текущими потребителями. Не внедрять параллельный «псевдо-Rules» adapter в Job Seeker. Если действие нельзя реализовать без изменения/размывания публичного контракта Rules, остановить эту ветку и вернуть вариант пользователю.
- Нужна проверка доступности `jev-1.13.0` для новой Noul формы и синтетическая проверка shape/range ответа. Если версия недоступна, не переходить молча на `jev-latest`: подготовить отдельный model version change и проверить его до реализации.
- Локальная schema потребует отдельной additive migration и защищённого recovery DB; production migration/deploy не разрешены этим design/implementation slice.
- Источники вакансий могут иметь `unknown` mode или неполный текст. Для S1 synthetic input это explicit; решение о детальном extraction полноты источников относится S3.

## Приёмка RWR.S1

- Synthetic eligible-вакансия проходит Job Seeker → Cockpit Rules passthrough → Jev Noul → неизменённый answer → отдельное хранилище.
- Нулевой, единичный и промежуточный валидный Noul fraction сохраняются без коррекции; валидация ограничена типом/конечностью/диапазоном и model identity.
- Синтетические примеры различают worldwide, Europe (Албания включена), EU-only (Албания исключена), запрет только одной страны/группы при разрешённых других странах, unknown и onsite exclusion. Основная таблица Rubric cases должна быть зафиксирована до реализации.
- Отсутствующий result остаётся NULL/без completed результата, а не нулём. Duplicate create, retry, истёкшая lease и завершённое значение защищены от перезаписи.
- Ни один тестовый/рабочий вызов не содержит candidate facts или candidate-specific data; обычные логи не раскрывают текст объявления, ответ Jev или ключ.
- Текущий fit и существующая борда/triage не меняют поведение. В S1 не добавляются колонка, сортировка, filter или действие отклика.

## Проверка, не входящая в этот документ

Они не включают реальные объявления/кандидатские данные и production. Результаты и source provenance должны быть записаны до изменения FACT/Trust.
