# Job Machine — Decomposition Map

## JFIT — оценка соответствия кандидата вакансии

16.10.2026: согласованы [Intent](vacancy-fit-intent.md), выбор Jev, [проект Brainstorming](superpowers/specs/2026-10-16-vacancy-fit-design.md) и продуктовые уточнения Grill Me. Проект и план S2 приняты; локальная Story реализуется. Это новый Epic; существующие recovery/GHL/OBS ветки сохраняются.

### Staging JFIT до декомпозиции

**A — локальная проверенная функция целиком.** Однократная оценка новых вакансий для активных кандидатов, неизменяемый вход, технические повторы, наблюдаемая диагностика, борда только с Jev и фронтенд-сортировкой всей выборки. Проверяется в локальном recovery-контуре и на synthetic данных; реальный API проверяется на синтетическом входе при доступном разрешённом аккаунте. Это выбранный срез. Выполнение в production и изменение production-схемы исключены.

**B — эксплуатационная доставка функции.** Проверка реального API и условий обработки кандидатских данных, ограниченные ресурсы, воспроизводимое включение без backfill, диагностика и откат с сохранением финальных результатов. Требует отдельного определённого задания на production-миграции/redeploy. Полный Intent сохраняется; готовность A не закрывает Epic.

Отдельного урезанного MVP нет: срез A охватывает всю локальную возможность. Разделение A/B следует существующей границе полномочий и сред, а не исключает сложные требования из функции.

**Staging текущей Story JFIT.S2 в срезе A.** Полный локальный автоматический охват: DB-level назначение каждой новой вакансии на первом verified INSERT/переходе, durable подготовка ATS/facts, запуск Jev worker из периодического pipeline, повторы, диагностика и synthetic/recovery-DB доказательства. Все пути прямой записи покрываются trigger; production schema/runtime и реальные факты вне среза.

### Проход JFIT среза A → Story

| ID | Ценность и ответственность | Проверяемый результат и границы |
|---|---|---|
| JFIT.S1 | Для одной допустимой новой пары получается однократная оценка Jev по согласованной рубрике | Все подтверждённые факты, переносимый опыт, неизвестное, приоритет обязательного требования; типизированный адаптер, точная версия модели, валидация 0–100, неизменяемый вход/финал, технические повторы и диагностика. Synthetic качество и отказные сценарии; внешний API на synthetic входе при доступности |
| JFIT.S2 | Новые вакансии автоматически получают отдельную оценку для каждого активного кандидата | Все пути создания vacancy, атомарная постановка, отсутствие backfill, дедупликация, граница активации/включения и конкурентность; деактивация не отменяет уже созданное; старый triage не управляет новой оценкой |
| JFIT.S3 | Пользователь видит и сравнивает Jev для всей выбранной совокупности в борде | Только Jev, 0≠NULL, у истории «—», числовое распределение без A/B/C/D; весь набор сортируется на фронтенде до пагинации; согласованность частей/кандидата/фильтров, свежесть, явный отказ вместо усечения; интегрированная локальная приёмка и релевантный регресс |

За пределами текущего среза: **JFIT.S4** — оператор получает функцию в рабочем контуре lab-do с проверенными API/data-handling, включением, health, ресурсами и откатом. Это Story среза B, пока свёрнута. Её полная декомпозиция выполняется отдельно после авторизованного актуального preflight.

Полнота A: S1 владеет смыслом и жизненным циклом одной оценки; S2 — автоматическим охватом новых пар; S3 — пользовательским потреблением и доказательством всей локальной возможности. Внутренние части адаптера/БД/worker не выделяются в искусственные Story без самостоятельной ценности.

Зависимости: S2 зависит от контракта и жизненного цикла S1; S3 зависит от данных S1 и проверки end-to-end S2. S4 зависит от A и отдельного задания на production-изменения. Циклов нет. Неразрешённый реальный API/data-handling не подменяется успехом fake-клиента.

**Heart Statement:** новая вакансия даёт пользователю неизменяемое число соответствия конкретного кандидата, по которому можно сравнить всю выбранную совокупность. **Heart Core / слой0:** S1 и S3. **Слой1:** S2 — автоматический охват, необходимый для полноты Heart. **Heart Slice A:** S1+S2+S3. Маршрут: S1 → S2 → S3; ближайший путь S1 закрыт в проверенной локальной области, текущий — JFIT.S2 → Task. S4 свёрнута.

Технические ворота: перед исполнимым планом S1 сверить официальный Score API/нормализацию/model ID, существующие источники фактов и защищённое хранение снимка; перед планом S3 определить ресурсно ограниченный протокол полного снимка. S2 опирается на verified trigger, безопасную сборку фактов и существующий worker S1; контракт конкурентной активации должен сериализовать любые прямые active INSERT/UPDATE на уровне БД. Это исследуемые агентом факты и инженерные решения. Существенное изменение состава/замысла возвращает затронутую ветку в Brainstorming. Формального утверждения карты не требуется.

### Отдельный проход JFIT.S1 → Task

Технический контракт Score/Choice сверён по официальной документации; нормализация, закреплённый model ID и отсутствие SDK отражены в проекте. S1 получает типизированные факты; автоматический сбор всех канонических источников остаётся в S2. Защищённый снимок хранится в БД рабочего контура, а не в audit/logs/Git; локальные DB проверки используют только recovery-cluster.

| ID | Исполнимый результат | Доказательство |
|---|---|---|
| JFIT.S1.T1 | Адаптер HTTP строит неизменяемый запрос по рубрике и возвращает валидированное число с обязательным override | Fake transport: Score 0..4 → 0..100, округление, три Choice-исхода, malformed/errors, отсутствие утечки payload/key |
| JFIT.S1.T2 | БД хранит один вход и один завершённый результат пары, с арендой и историей безопасных технических метаданных | Recovery DB: уникальность, запрет перезаписи input/completed, lease fencing, конкурентное завершение, точный повтор сохранённого запроса |
| JFIT.S1.T3 | Worker завершает назначенные задания и восстанавливается после сбоев, не затрагивая triage/submit | Fake clock/transport + recovery DB: retry/backoff, истёкшая аренда, blocked config, deactivation, restart; synthetic quality/live probe отделены от unit |

Зависимости: T3 зависит от T1 и T2. T1/T2 могут использовать согласованный контракт независимо, но выбран последовательный маршрут T1 → T2 → T3. Heart/Core S1 — T1 и T2 (смысл и неизменность оценки), слой1 — T3 (исполнение и восстановление); Heart Slice — все три. **Task reached:** дочернего backlog нет. Ближайший результат — T1, затем локальная S1 целиком. [План S1](superpowers/plans/2026-10-16-vacancy-fit-s1.md) раскрывает только эти Task, не новую карту.

S1 не включает автоматический обход исторических/новых вакансий, составление UI или production-доставку. Реальный API и качество нельзя объявить проверенными по fake transport. При отсутствии аккаунта API-проба остаётся незакрытой проверкой; доступные локальные результаты выполняются независимо.

### Отдельный проход JFIT.S2 → Task

Граница готовности: цель Story — локально назначить и выполнить первичную оценку для каждой новой verified vacancy/active-candidate пары; Task должны совместно доказать атомарный охват, безопасное восстановление подготовки и фактическое включение в периодический цикл. Existing production schema/deploy остаются вне Story.

| ID | Исполнимый результат | Доказательство |
|---|---|---|
| JFIT.S2.T1 | Миграция создаёт durable preparation/recipient queue и DB triggers, фиксирующие активный набор при verified INSERT/первом переходе без backfill | Recovery DB: прямые INSERT/UPDATE покрыты, повторы/dedup и empty set, rollback целостности, конкурентные active INSERT/UPDATE линейно упорядочены advisory lock-ом |
| JFIT.S2.T2 | Preparation worker получает содержимое вакансии и разрешённые факты, создаёт immutable S1 задания с повторами/blocked recovery | Synthetic unit+DB: все ATS families через существующие клиенты, excerpt, allowlist только locked, no content, transient/permanent ошибки, повтор после сбоя между create_job и child commit; payload не попадает в логи |
| JFIT.S2.T3 | Периодический auto pipeline подбирает обе очереди ограниченными порциями и изолирует ошибки от остальных стадий | Fake Jev transport + recovery DB: очередь подбирается и без новой verify в цикле, batch остаток сохраняется, нет вызова внутри trigger, pending S1 завершается/повторяется, остальные pipeline stages продолжаются |

Зависимости: T1 и T2 можно реализовывать параллельно по зафиксированному DB-контракту; их интеграционные DB проверки затем подтверждаются вместе. T3 зависит от обоих. S1 уже предоставляет immutable store/worker contract. Heart/Core S2 — T1 и T2 (назначение и неизменяемые факты), слой1 — T3 (автоматическое исполнение), Heart Slice — все три. **Task reached:** дочерний backlog не создаётся; план локальной Story S2 принят, декомпозиция дочерних Task не требуется. Review проводится один раз на собранной Story, как задано выбранным способом исполнения. [Проект S2](superpowers/specs/2026-10-16-vacancy-fit-s2-design.md); [план](superpowers/plans/2026-10-16-vacancy-fit-s2.md).

**Состояние S1 на 16.10.2026:** локальная S1 проверена: 1302 unit, 87 smoke, 369 DB и 2 schema-regression; 506 provenance hashes совпали. На синтетическом входе прошли 8 реальных запросов и worker→Jev→recovery DB (completed 99, затем idle). [Evidence S1](../audit/vacancy-fit-s1.md) — владелец результатов и ограничений качества. Реальная калибровка и условия хранения данных у провайдера не подтверждены.

**Состояние S2 на 16.10.2026:** локальная реализация T1–T3 прошла 1322 unit, 87 smoke, 382 guarded DB и 2 schema-regression. Независимый Story review выявил и после исправлений закрыты: утечка исключений, потеря proof claim, retry некорректных канонических фактов и lease короче ATS retry budget. [Evidence S2](../audit/vacancy-fit-s2.md). Production migration/runtime не выполнялись. Следующий маршрут — S3; S4 требует отдельного production-задания.

## GHL — Greenhouse Live, активный маршрут

15.10.2026 пользователь утвердил [Intent](greenhouse-live-intent.md), [технический проект](superpowers/specs/2026-10-15-greenhouse-live-design.md) и политику взаимодействия. Designing → Brainstorming → Grill Me завершены; принятые ответы используются повторно. Открытых вопросов замысла нет. Это новый эпик развития существующей BOARD.S1, а не вложенный эпик или повтор её реализации.

### Staging до декомпозиции

**A — локальная борда с доказанным автообновлением.** Полный Greenhouse-отчёт, ограниченное чтение, честная свежесть, сохранение native взаимодействия, новый установленный wheel и предметная/графическая приёмка. Результат можно проверить независимо от новой инфраструктуры. Текущий срез — A; существующие production workers не меняются.

**B — рабочее размещение на lab-do через существующий демон.** Отдельный сервис и минимальные права чтения, воспроизводимый запуск, диагностика, туннель и откат борды. Начинается после A, актуального read-only preflight и отдельного определённого задания на изменения среды. Все эти требования остаются в полном Intent; A не закрывает эпик.

### Проход 1: GHL → Story

| ID | Наблюдаемый результат | Приёмка и граница |
|---|---|---|
| GHL.S1 | Оператор работает с автоматически обновляемым достоверным Greenhouse-отчётом без потери рабочего контекста | Срез A; source parity, freshness/race/interaction tests, установленный общий wheel и реальная browser acceptance; без production-доставки |
| GHL.S2 | Оператор открывает эту борду с lab-do через существующий демон; её отказ и откат не нарушают workers | Срез B; собственный read-only доступ, health, туннель, resource budget, проверенный rollback и identities до/после |

Полнота: S1 охватывает данные и рабочее поведение; S2 — целевую эксплуатацию. Новая история, submit, пересчёт фита, HH/Telegram и отдельная status page не входят в GHL. S2 зависит от S1 и эксплуатационного допуска. Heart — достоверный отчёт, которым можно пользоваться во время обновления. Core/слой0 — S1; слой1 — S2 как необходимая доставка. Heart Slice текущего staging — S1, полный маршрут эпика S1 → S2.

### Проход 2: GHL.S1 → Task

| ID | Самостоятельно проверяемый результат | Зависимости и доказательство |
|---|---|---|
| GHL.S1.T1 | Согласованный отчёт несёт canonical context, row identity и честный возраст; чтение ограничено deadline/admission | Действующий consumer; contract/unit и изолированные DB tests, stalled-worker admission и health isolation |
| GHL.S1.T2 | Общий engine управляет polling, одним текущим/одним pending snapshot и сроком пригодности | Утверждённый контракт; fake clock/transport, context/races/expiry/visibility/destroy; static mode совместим |
| GHL.S1.T3 | Native компоненты применяют один snapshot целиком, сохраняют view-state и соблюдают interaction barrier | T2; real DOM selection/copy/resize/menu/modal, expiry/recovery и отсутствие lifecycle leaks |
| GHL.S1.T4 | Новый immutable wheel подключён; локальная борда принята на synthetic и реальных read-only данных | T1+T3; installed-asset parity, baseline, live SQL parity, разрешённая browser acceptance, review и FACT |

Heart S1 — обновление не подменяет рабочие данные и не сохраняет их сверх срока. Core/слой0 — T2/T3; слой1 — T1/T4 как источник и доказательство. Heart Slice — все четыре Task. Семантический приоритет не меняет зависимости: маршрут T1 → T2 → T3 → T4. T1/T2 технически могут идти независимо по общему контракту; текущий план выбирает последовательное исполнение, снижая стоимость согласования двух репозиториев.

**Task reached:** дочернего backlog нет. T1–T3 готовы к исполнению; у T4 заранее известен gate реального Browser: сохранённый отказ доступа пока не снят. Остальные проверки выполняются независимо, но T4/A не закрываются только по DOM/HTTP. [Implementation plan](superpowers/plans/2026-10-15-greenhouse-live.md) содержит шаги этих Task, не вторую карту.

S2 остаётся свёрнутой до завершения A и актуального preflight; её смысл, зависимость и критерии результата определены, но неизвестные пути/права/ресурсы не превращаются в фиктивно готовые Task. Перед её планированием — отдельный проход S2 → Task без повторного согласования принятого замысла.

Преемственность: открытая аналитическая приёмка BOARD.S1.J3 включена в T4; исходная запись остаётся историей незакрытого gate, а не вторым активным заданием. Доставка BOARD.S3 принадлежит теперь GHL.S2. BOARD.S2 (системная status page) остаётся вне GHL и не запускается. Исполнение пользователь утвердил15.10.2026: последовательно здесь с независимым итоговым review. T1–T3 реализованы, T4 подключает wheel0.2.0a4; review4Important исправлены с RED/GREEN. T4/A остаются открытыми: сохранённый Browser deny и отклонённая автоматической проверкой новая live parity; общая DB-suite после прежнего discovery throttle failure повторно прошла345тестов, flakiness записана. [Evidence](../audit/greenhouse-live.md). Доставка B не начата, эпик не закрыт.

## Коррекция поставки Observer: OBS.S2

Пользователь сообщил, что графиков нет и страница почти не изменилась. Причина установлена: доставлена S1, а согласованная S2 ещё не реализована; карточки старого renderer не являются столбчатой диаграммой. Текущий маршрут переключён на S2 по обратной связи пользователя; полный Intent и S3/S4 сохраняются.

## Эпик OBS — проект развития Observer

Дата: 15 октября 2026. Статус: эпик принят, OBS.S1 реализована и проверена локально; S2–S4 открыты. Пользователь выбрал развитие существующей панели. Предыдущий маршрут восстановления ниже сохранён и автоматически не возобновляется.

Родитель: OBS, самостоятельная возможность достоверного наблюдения за существующим Job Machine. Уровень этого прохода: Epic → Story. Рабочий идентификатор OBS не меняет существующую нумерацию. Включение OBS в Project предполагает передачу ему представления данных из интерфейсной части E3; reconciliation, сохранность истории и backup/restore остаются E3. Уточнение границ принято вместе с проектом; OBS владеет интерфейсом, E3 — восстановлением данных.

Staging: выбран весь OBS как один ценностный срез. Частичные Story проверяемы самостоятельно, но эпик принимается только с выполнением общих гарантий достоверности. Новая аналитика, управление и восстановление данных не являются отложенными частями OBS.

| ID | Story: ценность и ответственность | Критерий завершения |
|---|---|---|
| OBS.S1 | При возвращении оператор различает доступность источников, подтверждённую работу, ошибки и недостаток свидетельств | Время/смысл активности установлены либо явно недоступны; local health, DB и контейнеры не подменяют работу; нулевая activity не означает idle; сбои/частичный ответ/stale/expiry/recovery различимы |
| OBS.S2 | Оператор понимает фактический прогресс по существующим счётчикам | Определены источник, единица и охват; состояния вакансий/заявок/попыток разделены; отсутствующие данные не стали нулями; неподтверждённая сквозная воронка не показана |
| OBS.S3 | Оператор находит заявку и понимает её исход или причину остановки | Таблица сохраняет идентичность кандидата и заявки; все полученные статусы различимы; ограничение последних N видно; заявка находится по известному ID вне этой выборки; детали и ошибки доступны на странице |
| OBS.S4 | Оператор находит результат выбранной заявки и понимает его доступность | Существующие артефакты связаны с правильной заявкой; безопасная ссылка открывается; runtime path, отсутствующий файл и неизвестная доступность различимы; нет выдуманной ссылки и восстановления файлов |

Полнота: S1 охватывает возвращение и достоверность состояния, S2 — понимание отбора в пределах данных, S3/S4 — поиск заявки и результата. Исследование проблемы проходит через S1 и детали S3/S4. Read-only, доступность интерфейса, границы данных и безопасное отображение обязательны для каждой Story; отдельные технические контейнеры ради них не создаются.

Зависимости: все Story используют существующую E1-панель и доступные источники lab-do. S4 зависит от контекста заявки S3. S2 не блокируется S1, но разделяет его контракт свежести. Новые production API E2 не предполагаются доступными. E2.S3 и исправления E3 не блокируют показ честного неизвестного/недоступного состояния; они не могут быть скрыто включены в OBS. Доступ к файлу может оказаться недоступен без отдельной доработки; S4 обязана показать ограничение, а не расширять инфраструктуру.

Heart Statement: оператор понимает фактическое состояние Job Machine и конкретной заявки, отличая доказанное от неизвестного.

Heart Core: S1 и S3. Слой 0 — S1/S3; слой 1 — S2/S4 как раскрытие масштаба и результатов работы. Heart Slice: S1+S3; транзитивных блокирующих Story внутри OBS нет. S4 не становится ядром лишь из-за зависимости от S3.

Маршрут: OBS → S1; уточнить источники полезной активности, последней ошибки и частичных отказов, затем отдельным проходом S1 → Task. Далее S3; S2/S4 сохраняются свёрнутыми на уровне Story. До решения технических вопросов подробный план и фиктивно готовые Task не создаются. Формального согласования Heart/приоритетов не требуется.

Проверка карты: четыре непосредственные Story, Task не добавлены, E3 не дублируется, полный исходный Intent сохраняется. Эта секция не утверждает реализацию Observer или завершение восстановления.
